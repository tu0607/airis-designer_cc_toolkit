---
description: デザイン（言葉・ラフ画・Figma・Claude Design いずれでも）をルールに従ってコード化し、別リポジトリへ Push する
---

あなたは Airis のデザイン→コード変換フローを実行します。
`CLAUDE.md` に定義されたフロー全体（1〜11）に**そのまま従って**ください。

**先に `CLAUDE.md` の「絶対に守る 4 つの原則」を読み、例外を作らないこと**:

1. GitHub のブラウザ画面での手動操作を案内しない（コミット・Push・PR は Claude が `git` / `gh` で行う。トークンも同じ）
2. Push 前にローカルでテスト・ビルド・Storybook 起動をしない（検査は GitHub Actions、見た目は公開 Storybook）。**ただし `style-dictionary build` と `scripts/` の 4 本（`effective-scale` / `contrast` / `lint-naming` / `selfcheck`）と `shadcn` CLI は例外**（ビルドでもテストでもない）
3. デザインソース側の不備を勝手に埋めない（ステップ 7 の診断レポートで操作者に返す）
4. トークンにない値をコードに書かない（逆引き表に無ければ診断へ回す）

進め方:

1. **挨拶・前置き・意気込みを書かない。** コマンドを打った本人は何が起こるか知っているので、いきなり最初の質問（引数があればその解釈結果）から始める。非エンジニア向けの配慮は「挨拶」ではなく**質問を平易な日本語にすること**で果たす。
2. **デザインソースを確定する**（言葉での要望 / ラフ画・参考画像 / Figma / Claude Design / 参考サイト）。引数や文脈から自明なら聞き直さない。
3. `CLAUDE.md` のフローを順番に、**1 ステップずつ対話的に**進める。
   - 言葉・ラフ画の場合: デザイン提案（HTML モック）→ 合意してからコード化。
   - Figma の場合: MCP（`figma-dev-mode` / `figma-framelink`）で取得。未接続なら `/setup` を案内。`get_code` の出力は**構造の資料**として読み、値はそのまま採用しない。
   - Claude Design の場合: デザイン一式を「確定デザイン」として受け取り、コードはルール準拠で生成し直す（`CLAUDE.md` 2-C）。途中からの確認・移行にも対応。
4. **作るものを確定する**（`CLAUDE.md` ステップ 3）。**Web / ネイティブの判定と、Web の 3 ターゲット選択を 1 つの質問に混ぜない**（混ぜると LP（Astro）/ コンテンツサイト（Next.js）が選択肢として現れなくなる）。
   - 判断がつかないときは **3 ターゲットの表をそのまま見せて選んでもらう**。自動検知や `config` の固定値で決まった場合も、**決定と理由を 1 行で伝えて確認を取る**（フレームワーク選定は後戻りしにくいため、黙って決めない）。
5. `rules/common.md` と該当ターゲットのルールを**必ず読み込む**（`CLAUDE.md` ステップ 4）。**次の診断でアーキテクチャ適合を検査するために必要**なので飛ばさない。
6. **Push 先（URL / ブランチ / 配置先）を確認し、作業ツリーをクローンする**（`CLAUDE.md` ステップ 5）。**7・8・9 はこの作業ツリー上で動く**ので後回しにしない。
   - `node_modules/` が無ければ `npm ci` の実行可否を確認する（無いと 7 のトークン変換と 8 の実効スケール実測ができない）。
   - `tokens/` / `config/` / `tests/` / `.github/` は配置先に関わらず**リポジトリのルート直下**。
7. **トークンを確定し、「値 → トークン名」の逆引き表を作ってチャットに提示する**（`CLAUDE.md` ステップ 6 / `rules/common.md` §2）。
   - **Figma ルートのトークンは 4 択**（`tokens.figmaExport`: `tokens-studio` / `custom-plugin` / `plugin` / `claude`）。未設定なら**その場で選んでもらい保存**する。どれも対等な選択肢として提示し、特定の方法を推さない。
   - プラグインで受け取った JSON は **① 正本 `tokens/` への取り込み（`styles/tokens.css` の生成）と ② 逆引き表の作成の両方**に使い切る。受け取っただけで終わらせない。
   - トークンは**生成コードと同じブランチ・同じ PR** に入れる（Claude がコミット・Push する）。順序の段取りは不要。
8. **変換前診断を行う**（`CLAUDE.md` ステップ 7 / `rules/common.md` §9）。**コード生成の前に必須。3 カテゴリすべてを毎回通す**（① だけで終わらせるのが診断漏れの典型）:
   - **① デザインソースの不備** … 未トークン化の直値 / 絶対配置 / 無名レイヤー / 命名 / 未 Component 化 / 変換できない挙動
   - **② 設計の抜け** … hover・focus・disabled・error・空・読み込み中などの**状態**、レスポンシブの他ブレークポイント、長文・0 件時の振る舞い
     - **コントラストは目視で判断しない**。`node scripts/contrast.mjs <作業ツリー> text-content-muted:bg-surface …` で**比を実測**する（重なっている組み合わせだけ渡す）。**ここで拾えば a11y の CI が赤くなる前に Figma を直せる**（`rules/common.md` §9.2）
   - **③ アーキテクチャ非適合** … **Tailwind のスケールに乗らない数値**、shadcn/ui の部品に当たらない UI、CVA の語彙に乗らないバリアント
     - 数値は暗記せず **`node scripts/effective-scale.mjs <作業ツリー> spacing:13px radius:20px …` で実測**する（版とプロジェクトの `@theme` でスケールが変わる）。取得できなければ「未実施」と正直に報告する
   - 各項目は**「どこが・何が問題か・どう直すか」**の 3 点。数値のズレには**寄せ先の候補**（`13px → p-3(12px) か p-3.5(14px)`）を必ず添える。スクリプトの出力をそのまま使い、暗記で書かない。
   - 「A. Figma を直して再実行」「B. この前提で進める（TODO + PR 本文に記載）」を**必ず操作者に選ばせる**。黙って B に進まない。
   - 該当ゼロのカテゴリは 1 行で済ませる。全部なしなら「診断: 問題なし」の 1 行。
9. **作業ツリーへ直接コード生成**する（`output/` 経由で配置し直さない。`CLAUDE.md` ステップ 8）。
   - **書き始める前に、該当ターゲットのルール冒頭の「生成直前チェックリスト」を読む**（`rules/web-app.md` の先頭）。
   - **shadcn/ui で表せる部品は `npx shadcn@latest add <部品>` で導入**する（手書きすると本物の API からずれる）。
   - ワークフロー等の相対パスは 6 で確認した配置先に合わせて置換する。
10. コンポーネントごとに **Storybook 用のストーリーも生成**する（`config` で無効化されていない限り）。
   - Storybook は**ローカル起動を前提にしない**。Web では **3 層のテスト（①コンポーネント ②ストーリー ③VRT）を GitHub Actions で回し、開発ブランチの Storybook を GitHub Pages へ公開する**ワークフロー雛形もあわせて生成する（`storybook-test-and-publish.yml` / `story-test.yml` ほか。`ci.yml` のような汎用名は使わず、何を検査するかを名前に書く。Storybook のビルドは全体で 1 回だけ。③ VRT は test-runner ではなく `@playwright/test` で行う。`CLAUDE.md` ステップ 9 / `rules/web-app-storybook.md` §2・`rules/web-app-ci.md` §1）。
   - **生成したテストを Push 前に走らせない。** 足りない devDependencies は**報告するだけ**（`package.json` を勝手に書き換えない）。
   - 実装者向けの案内は **PR 本文の冒頭に数行 + チャットで一言**で済ませる。**`SETUP_GITHUB.md` のような手順書ファイルは作らない**（`rules/web-app-storybook.md` §3）。
   - **Pages の閲覧範囲と URL は推測せず `gh api repos/<owner>/<repo>/pages` で確認**してから伝える（**「Private だから安全」は誤り**。手順は `CLAUDE.md` ステップ 9-1、判定表は `rules/web-app-storybook.md` §2）。
11. **セルフチェックを通す**（`CLAUDE.md` ステップ 10-1）: `node scripts/selfcheck.mjs <作業ツリー> [--src <配置先>] --tsc`
    - **ERROR は Push 前に直し、0 になるまで再実行**する。「CI が教えてくれる」で流さない。特に **`class-exists`（`@theme` に無いクラス）は CI が一切捕まえない**ので必ず潰す。
    - **WARN は勝手に直さず報告**する（判断は操作者のもの）。残した WARN は PR 本文にも書く。
    - 型検査がスキップされたら「型検査は未実施」と必ず報告する。
12. `git diff` で差分を提示して確認を取り、**コミット → Push → `gh pr create` まで Claude が行う**（トークンも含める）。破壊的・外部影響のある操作は必ず事前確認を取る。
13. **CI の結果まで見て、デザイナーに翻訳して伝える**（`CLAUDE.md` ステップ 11-1）。「PR を出したので終わり」にしない。
    - `gh pr checks` → 赤いジョブを `gh run view --log-failed`。落ちた層はジョブ名で分かる。
    - **実装起因（Claude が直す）とデザイン起因（Figma の Variable を直す）を切り分ける。** 切り分けずに「Figma を直してください」と言わない。**a11y のコントラストは `cn()` 未対応で文字色が消えているだけの場合がある**（`rules/web-app-styling.md` §5）。
    - デザイナーに返すときは**規則 ID を貼らず日本語に翻訳**し、`scripts/contrast.mjs` の寄せ先候補から選ばせる。

引数があれば対象の指定（要望テキスト、画像パス、Figma URL など）として解釈してください: $ARGUMENTS
