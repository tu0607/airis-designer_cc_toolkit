---
description: ドキュメントの厳密確認（スタイル・誤り・矛盾・不足・蛇足）と、本質を保った圧縮を 3 セット繰り返す
---

ドキュメントを**確認 → 修正 → 圧縮**の 1 セットとして、**3 セット**繰り返します。
1 セットで見つかるのは表面的な誤りだけです。**セットを重ねるほど「実装と食い違っている記述」が出てくる**ので、3 セット目まで手を抜かないこと。

## 対象

- 引数があればそれ（ファイル / ディレクトリ / 節名）。
- 無ければ**直近の作業で触ったドキュメント**（`git diff` / `git status` と会話の文脈から特定し、対象一覧を提示してから始める）。
- **コード内のコメントもドキュメントとして扱う。** 誤った記述はコメントに潜みやすい。
- 対象外のファイルは勝手に書き換えない。**ただし対象と矛盾している記述を他所で見つけたら、その矛盾の解消だけは行う**（見つけた旨を報告する）。

## 各セットで確認すること

### 1. 記述内容が間違っていないか（**最重要。ここに一番時間を使う**）

**文章だけを読んで判断しない。実装・設定・出力と突き合わせて裏取りする。**

- **数値・件数・固有名は必ず数え直す。** 「検査項目 19 個」「CI 4 本が参照する」「5 分類」のような記述は、コードを `grep` / `awk` で数えて一致を確認する。
- **例示が本当にその挙動になるか確認する。** 正規表現・条件分岐の例は、実際に short script で流して確かめる（除外されるはずの例が実は最初から対象外だった、という誤りが起きる）。
- **「〜が正」と書かれた参照先が実在するか**（節番号・ファイルパス・コマンド名・オプション名）。
- 実装が持つ条件が記述から漏れていないか（除外条件・スキップ条件・上限）。

### 2. 記述内容に矛盾がないか

- 同じ事実が 2 か所以上にある場合、**両方が同じことを言っているか**。
- 「A が正」と書きながら A 側に該当記述が無い、という参照切れ。
- 表と本文、要約と詳細の食い違い。

### 3. 記述内容に不足がないか

- 実装にあって記述が無い挙動（特に**除外・例外・トレードオフ**）。
- **「なぜそうするか」が無い規則**は守られないので、理由を 1 行足す。
- 記号（`※` 等）を使ったのに凡例が無い。

### 4. 蛇足・重複していないか

- 同じ説明が表と本文の両方にある → **表は印だけ、詳細は 1 か所**。
- 変更履歴の残骸（「今までどおり」「従来は」）。読者は変更前を知らない。
- 読者の判断を変えない前置き・言い換え。

### 5. スタイルミスが無いか

- Markdown: 表の列数、リストのインデント（継続段落は 4 スペース）、コードフェンスの開閉と言語指定、見出しレベルの飛び、リンク切れ。
- 文体: 同一ファイル内での句点（`。`）の有無・敬体常体・太字の使い方を揃える。**太字が多すぎると強調が効かない。**
- コード例: インデント（Python は特に）、言語と実際の構文の一致。

### 6. 単一責任が壊れていないか（**1 ファイルに複数の文脈が溜まっていないか**）

ドキュメントにも単一責任の法則を適用する。**1 ファイル = 1 つの文脈**。
文脈が混ざったファイルは、読む側が「自分に関係ある部分」を切り出せず、書く側も追記先を迷って**さらに混ざる**（容量が爆発する原因）。

- **150 行未満なら複数の文脈を許容する。** 分割の手間と参照の増加が読みやすさの利得を上回るため。
- **150 行以上のファイルは、節ごとに「何の文脈か」を数えて判定する。** 文脈が 2 つ以上あり、かつそれぞれが独立して読めるなら**分割候補**として報告する。
- **分割は自動で行わない。** 節の参照（`§N`）が他ファイルから張られていることが多く、**参照の付け替えを伴う**ため。**分割案・移動先・付け替えが必要な参照の件数を示して判断を仰ぐ**。
- 例外として次は分割しない:
  - **コード例・雛形が行数の大半を占めるもの**（文脈は 1 つで、単に長いだけ）
  - **入口ファイル**（索引 + 各文脈への振り分けが役割。ただし入口に実装詳細を書き溜めていないか確認する）

```bash
# 行数の一覧（150 行以上を洗い出す）
wc -l <対象...> | sort -rn

# 節ごとの行数（どの文脈が膨らんでいるか）
python3 -c "
import re, sys
L = open(sys.argv[1]).read().split('\n')
H = [(i, l) for i, l in enumerate(L) if re.match(r'^#{2,3} ', l)]
for j, (i, l) in enumerate(H):
    print((H[j+1][0] if j+1 < len(H) else len(L)) - i, l)
" <対象.md> | sort -rn
```

> **このファイルに「半角ドル記号 + 数字」を書かないこと**（`＄0` `＄1` のような形。ここでは説明のため**全角**の `＄` を使っている）。
> スラッシュコマンドの引数がそこへ展開され、**コマンド例が壊れたまま渡ってくる**（`awk` で全行を変数に入れる書き方が、引数の文章に置換された実例あり）。上の節ごとの行数を `python3` で書いているのはそのため。
> 引数の受け取り口（`＄ARGUMENTS`）だけは意図的な置換なので使ってよい。

## 圧縮の原則

**本質を曲げない。** 短くすることではなく、**同じ判断ができる状態で短くする**のが目的。

削ってよい: 冗長な言い換え / 変更履歴の残骸 / 過剰な太字 / 重複した説明 / 判断に影響しない例示の 3 個目以降。

**削ってはいけない**:

- **禁止事項とその理由**（理由を削ると「なぜダメか」が失われ、いずれ破られる）
- **トレードオフ・既知の穴**（「ここは検査されない」は消してはいけない情報）
- **例外・除外条件**
- **具体例そのもの**（1 個は残す。抽象論だけにしない）
- **数値の根拠**（「実測する」「決め打ちしない」という指示）

## 各セットの終わりに機械的検証

```bash
# Markdown の表の列数（列数がすべて同じであること）
awk '/^\|/ {n=gsub(/\|/,"|"); print FILENAME":"NR": "n}' <対象.md> | sort -u -t: -k3

grep -nE ' +$' <対象>              # 行末空白
grep -c '<参照している節見出し>' <対象.md>   # 参照先の実在
```

- **コードやコメントに触ったら、対象スクリプトを実行して挙動が変わっていないことを確認する**（テストやフィクスチャがあれば流し直す）。
- 数値を書き換えたら、**書き換えた根拠のコマンドと出力を報告に残す**。

## 報告

- **セットごとに**「何を見つけたか / どう直したか」を分けて示す（3 セットまとめて報告しない。どのセットで何が出たかが次回の指針になる）。
- **事実誤りは必ず裏取りの根拠を添える**（数え直したコマンドの出力など）。
- 圧縮の結果を行数・文字数で示す。
- **判断が必要なものは直さずに提示する**（本質に関わる削除、仕様そのものへの疑義）。

## やらないこと

- **裏取りせずに数値を書き換える。** 「たぶん違う」で直すと誤りが増える。
- **短くするために本質を削る。** 迷ったら残して報告する。
- **対象外のファイルを圧縮する。** 矛盾の解消だけに留める。
- **1 セットで終わらせる。** 3 セット目に「実装と食い違っていた記述」が出るのが普通。
