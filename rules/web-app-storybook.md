# Web アプリ Storybook ルール — 書き方と公開

`web-app.md` の一部。**ストーリーの書き方と公開（GitHub Pages）**を定めます。
ストーリーを検査に使う仕組みは `web-app-testing.md`、ワークフロー雛形は `web-app-ci.md`。

## 1. ストーリーの書き方

各コンポーネントに `<コンポーネント名>.stories.tsx` を同ディレクトリに生成する（`config` で無効化されていない限り）。

- **CSF3** で書き、`Meta` / `StoryObj` に型を付ける。`title` はレイヤー付き（例: `ui/Button`, `common/SearchField`, `features/orders/OrderTable`）。
- Figma のバリアント・状態（variant 違い、`isDisabled`、error、サイズ違い等）を**個別ストーリー**として列挙 → **Autodocs** がドキュメント化。
- **play 関数**で「操作 → 結果」を動作テストとして書く（`@storybook/test` の `userEvent` / `expect` / `fn`）。ストーリー名は「何ができるか」の文章にする。
  - **`getByRole(..., { name })` の名前は実装の読み上げ名からコピーする**（「前のページ」と `aria-label="前のページへ"` のような 1 文字違いで落ちる）。**記憶で書かず、生成したコンポーネント側の文字列を見て書く**。
  - **Radix のロービングフォーカス**（RadioGroup / Tabs / Toolbar 等。グループ内で Tab 移動せず矢印キーで移動する仕組み）を矢印キーで操作するストーリーは、**先に起点となる項目を `click()` か `focus()` してから**キー操作する。起点が無いとフォーカスがどこにも無く、矢印キーが効かない。
- **`play` を付けないのが正しいケースもある**（セルフチェックは `story-play` を **WARN** で出す。ERROR ではないのは判断が人のものだから）:
  - **操作対象が無いドキュメント用ストーリー** — トークン一覧・アイコン一覧・書体見本のギャラリー。操作が存在しないので書けない
  - **表示のみの部品**（バッジ・区切り線など状態を持たないもの）
  - **形だけの `play` は書かない。** 「要素が存在する」だけを確認するものは**検査を通すための飾り**であり、壊れても気付けないので価値が無い（むしろ「テストがある」と誤認させる）
  - WARN は**報告して操作者が根拠を持って了承する**もの（`CLAUDE.md` ステップ 10-1）。上のどれに当たるかを添えて報告する。
- **a11y アドオン**でアクセシビリティを検査対象にする。
- **トークン一覧ギャラリーは a11y で落ちない作りにする**（`tokens.ts` の生成は `web-app-styling.md` §2.1）。`parameters.a11y.test: 'error'` は全ストーリーに当たるので、素直に作ると**部品の不具合ではないのに CI が赤くなる**:
  - **色見本の中に文字を置かない** — 見本の上の文字は「読めない組み合わせ」として検出される
  - **説明文の明度を `opacity` で落とさない**（コントラスト違反になりうる）
- ストーリーは**コンポーネント生成と同時に自動で付いてくる**（後から書き足す作業ではない）。以後は「**新しい状態・仕様 = 新しいストーリーを追加**」「**バグ修正 = 再現ストーリーを追加**」で育てる。
- ストーリーの対象は**コンポーネント単位**。画面（pages）のストーリーは作らない（データ依存が強く Storybook 向きでない。画面は E2E で担保 = `web-app-testing.md` §3）。画面内の表示バリエーションは、それを構成するコンポーネント側のストーリーでカバーする。
- Storybook は**デザインの意図と実装が答え合わせをする唯一の接面（公式カタログ / 仕様の合意面）**として機能させる:
  - **掲載可否・見た目の合否判定は、stories の実装・基盤整備とは切り離して行う**（見た目の合意と実装作業を混ぜない）
  - 仕様・使い方のガイドラインが必要な部品には **MDX ドキュメント**も生成する（Autodocs で足りる場合は省略可）
  - デザインと実装に差異が出たら、議論は Storybook 上のストーリーを見ながら行う

## 2. 公開先は GitHub Pages（ローカル起動を前提にしない）

Storybook が「答え合わせの唯一の接面」である以上、**デザイナーが URL を開くだけで最新版を見られる**状態を既定とする。

> **Claude は Push 前にローカルで Storybook を起動しない・テストを走らせない**（`CLAUDE.md` 原則 2）。壊れていれば PR のチェックが赤くなり、見た目のズレは公開 Storybook で人が気付く。
> `npm run storybook` の案内は、**デザイナーから明示的に「Push 前に見たい」と言われた場合のフォールバック**に限る。

- 公開は **GitHub Actions で静的ビルド → GitHub Pages へデプロイ**（`web-app-ci.md` §1）。
  - **公開 URL は 2 種類あり、決め打ちしない**。Pages の access control が無効なら `https://<org>.github.io/<repo>/`、有効なら **`https://<ランダム>.pages.github.io/`**（推測不可能なホスト名で配信される）。
  - **URL は推測せず `gh api repos/<owner>/<repo>/pages --jq '{public, html_url}'` で実際の値を取得してから案内する**（`html_url` が正。`public` が閲覧範囲）。
- **公開元は開発ブランチ**（`storybook.deployBranch`。既定 `develop`）。答え合わせは「これから出るもの」に対して行うため。develop を使わない運用（`git.developBranch` が空）なら main を公開元にする。
  - デプロイは **開発ブランチへの push のみ**。PR ではビルドとテストだけ走らせる（PR ごとの一時公開が必要になったら別途検討する）。
  - GitHub Pages は**1 リポジトリに 1 サイト**。develop と main の両方を見せたい場合は `gh-pages` ブランチのサブディレクトリ配信（例: `/` = main, `/develop/`）に切り替える必要がある。**既定では develop の 1 面だけ**にし、必要になった時点で相談する。
- Storybook の静的ビルドは相対パス参照なので、Project Pages のサブパス配信（`/<repo>/`）でそのまま動く。**`base` を独自に設定しない**（設定するとサブパスで壊れる）。
- **公開のゲートは ① だけ**。カタログの中身は部品なので、公開可否は ① で判断する。
  - **② はゲートにしない**（別ワークフローで走るため `needs` で繋げない。画面の E2E はカタログの正しさとは別問題）。
  - **③ VRT の失敗でもデプロイを止めない**（差分は人が見て「意図した変更か」を判断するものなので、むしろ公開して見比べてもらう）。
- Pages の有効化（**Settings → Pages → Source: GitHub Actions**）は**リポジトリ管理者の手作業**。Claude は実行できないので §3 で必ず案内する。
- **公開範囲は事前に伝える。**「**Private リポジトリなら安全**」という思い込みが最も危険なので、**プランと access control の有無で判断する**:

  | リポジトリ | プラン | Pages サイトの見え方 |
  | --- | --- | --- |
  | Public | 任意 | **誰でも閲覧可**（検索に載る可能性あり） |
  | Private / Internal | Free | Pages 自体が使えない |
  | Private / Internal | **Pro / Team** | **誰でも閲覧可** ← リポジトリは非公開でも**サイトだけ公開される** |
  | Private / Internal | **Enterprise Cloud**（access control 有効） | リポジトリに read 権限のある**サインイン済みユーザーのみ** |

  - **判定は推測せず API で確認する**: `gh api repos/<owner>/<repo>/pages --jq .public` が `false` なら認証必須、`true` なら誰でも閲覧可（Pages 未設定なら 404）。GUI では **Settings → Pages** に「Visibility」欄があるかどうか（無い = そのプランでは制限できない）。
  - `public: true` になる構成で未公開プロダクトのデザインを載せる場合は、下記フォールバック（`artifact`）を選ぶ。
- **Pages が使えない場合のフォールバック**: デプロイジョブの代わりに `actions/upload-artifact` で `storybook-static` を残し、Actions の実行画面からダウンロードして開いてもらう（それも不可ならローカル起動を案内する）。`storybook.publish` で切り替える（`github-pages` = 既定 / `artifact` = 成果物のみ / `none` = 公開しない）。

## 3. 実装者への案内（PR 本文とチャットで済ませる）

**伝える 4 項目と伝え方は `CLAUDE.md` ステップ 9-1 が正**（Pages 有効化 / 公開範囲 / 確認先とタイミング / VRT が赤いときの意味）。
**GitHub の設定手順書ファイルをリポジトリに作らない**（`SETUP_GITHUB.md` のような生成物は不要）。読み手は PR を見る人なので、置き場所は PR 本文とチャットが正しい。手順書をリポジトリに残すと、設定が済んだ後も負債として居座る。

Web アプリで**追加して伝えること**:

- Pages の Source 設定に**保存ボタンは無い**（選んだ時点で反映）。**Settings タブが見えない場合は管理者権限が無い**ので、管理者に依頼してもらう。未設定だと `publish-to-pages` ジョブだけが赤くなる。
- **落ちた層はジョブ名で判別できる**（`component-test` = ① / `visual-regression-test` = ③ / `story-test` = ②）。
- baseline の更新ワークフローは `vrt-baseline-update.yml`（Actions タブ →「VRT の見本画像を更新」）。
- **Private リポジトリでは Actions の実行時間が課金対象**（Public は無料）。コストが気になる場合は `testing.vrtBranches` を `["main"]` に絞れる。
