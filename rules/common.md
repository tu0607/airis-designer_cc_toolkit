# 共通変換ルール

すべてのターゲット（Web / ネイティブ）に共通するルールです。

> このファイルはテンプレートです。自社の規約に合わせて調整してください。

## 1. 基本方針

- Figma の見た目を**ピクセル単位で盲目的に再現しない**。意味・構造・再利用性を優先する。
- Figma の Auto Layout は、レイアウトプリミティブ（Web: flex/grid、ネイティブ: Stack/Flex）へマッピングする。
- 生成コードは**そのままレビュー・保守できる品質**を目指す（読みやすさ・命名・分割）。
- **デザインソース側の不備を推測で埋めない**。設定が足りない / 間違っている箇所は、直し方を添えて操作者に返す（§9 の診断レポート）。

## 2. デザイントークン（最重要）

色・タイポグラフィ・余白・角丸・影などの値は**ハードコードしない**。
「トークン＝デザインの単語帳」の**正本は DTCG（W3C Design Tokens）形式の JSON** とし、Push 先リポジトリの `tokens/` 配下で扱う（`tokens-studio` 運用時は同期先リポジトリの `tokens/` が正本で、そこから取り込む）。
ターゲットごとの置き場所へは **Style Dictionary で機械的に変換**する。**Claude が手で書き写さない**（冪等性を優先）。

### トークンの構造（Core 最小 + プロダクト主体）

```
tokens/
├── core/                     # ブランドの根源（最低限: ロゴ・スペーシング・表現原則）
└── product/
    └── <プロダクト名>/
        └── mode/             # ★ この構造を必ず取る（プロダクト直下にトークンを置かない）
            ├── default/      # 必須。プロダクトの作り込みはここが主戦場
            ├── README.md     # モードと利用シーンの対応マッピング
            └── <モード名>/   # 必要になったら追加する差分（dark, high-contrast 等）
```

- **Core は最低限に保つ**（上から決めるのはブランドの根源だけ）。**プロダクトの個性は `product/` 側で作り込む** — UI の全体感まで画一化すると「どの画面も似たり寄ったりで飽きる」ため、統一ではなく調和を目指す。
- **プロダクトのトークンは必ず `product/<プロダクト名>/mode/default/` に置く**（`mode/` 構造の強制）。初期は `default` だけで作り込み、ダークモード・集中モード等が必要になった時点で `mode/dark/` のような**差分ディレクトリ**を追加する。**先回りでモードを作らない**。
- **適用順（差分の決着順）**: `core` → `product/<名前>/mode/default` → `product/<名前>/mode/<モード>`（モード有効時のみ）。Style Dictionary はこの順で結合する（後勝ち）。**差分が無ければ Core がそのまま流れるのが正常形**。
- **逆流禁止**: 上書きは差分として重ねる。上位（Core 等）の定義ファイル自体を書き換えない。
- モード名は **性質名の共通語彙**（`dark`, `high-contrast`, `compact` 等）を使う。利用シーン（現場 / カフェ / 家 等）との対応は `mode/README.md` でマッピング管理し、**シーン名をモード名・Token 名に使わない**（シーンは境界が定義できず何でも入るため、有限個のモードに畳む）。
- **昇格（下からの共通化）**: 最初から共通化しない。**2 プロダクト以上で同じトークン・同じモードが観測されたら**、Core への昇格を検討する（コンポーネントの昇格と同じ原則。`web-app.md` §3.1.1）。
- トークンの編集は **Figma 側で行うのが基本**（取り出し方は `tokens.figmaExport` の 4 択。CLAUDE.md ステップ 6）。Claude は値もモードも勝手に増やさず、必要なら「Core とプロダクトのどちらに足すべきか」を添えて提案する。

### 構造の全体像（「2 軸 + 土台」。出典: Spotify Encore を自社規模に合わせて改変）

**性質の違う要素を直列の層に繋がない**のがこの構造の要点:

```
【意思決定の軸（Token パイプラインが流れる）】   Core → product/mode/default → product/mode/<モード>
【成果物の分岐（層ではなくビルドターゲット）】   Style Dictionary の出力先（Web / 将来 iOS / Android）
【共有インターフェース】                        Storybook（デザイン意図と実装の答え合わせの場。GitHub Pages で常時公開）
【実装の土台】                                  Component 実装（shadcn/ui + Tailwind）/ Behavior（Radix Primitives = 選定済み依存）
```

- **Encore の教訓**: 失敗の本質は層の数ではなく「**柔軟性の供給過剰とガバナンス不足**」。だからガバナンス（昇格基準・承認の仕組み）を構造とセットで定義する（Web の具体則は `web-app.md` §3.1.1・`web-app-testing.md`）。
- **プラットフォーム別のサブシステム層は作らない**。パイプラインは最初からマルチ出力前提で設計する（初期設計なら出力先の追加はほぼゼロコスト。後付けは構造変更になる）。
- **Behavior（インタラクションロジック・a11y）は「層」ではなく「選定済み依存」**としてデザイン意思決定の外に置く。トークン / スタイルの意思決定と、依存の管理が**アーキテクチャ自体で分離**される。

### プラットフォーム差の吸収先（差分の種類で分ける）

「プラットフォームで違う」と言われたら、まず**どの種類の差分か**を判別して、対応する場所に振り分ける（Claude はデザイン確定時にこの判別を行い、どの箱に入れるかを添えて提案する）:

| 差分の種類 | 例 | 吸収する場所 |
| --- | --- | --- |
| **値の差** | 影・ブラーがそのプラットフォームで再現できない。タップ領域の要件が違う | **Build Target の上書き Token**。「実装できない / 操作的に現実的でない」場合のみ |
| **状況の差** | 「現場では iPad だからこの見た目に」など、デバイスと利用シーンの相関に由来するもの | **Mode**。プラットフォームは**シーンの代理変数**なのでトークンに焼き込まない。性質名のモード（例: `touch-large` + `high-contrast`）を定義し、「iPad なら既定で有効化」は**アプリ側の起動ロジック**にする。対応関係は `mode/README.md` に記録 |
| **構造・挙動の差** | 「このプラットフォームではこの要素を出さない」「この UI は実装不可なので別の標準 UI に置き換える」 | **コンポーネント・画面レイヤー**（トークンの守備範囲外）。画面構成の分岐、またはネイティブ標準への置き換え（`native.md`）で吸収 |

- デバイスとシーンの相関（iPad = 現場 等）は**変わりうる前提**で扱う。プラットフォームに焼き込むと相関が崩れた時に間違いになるが、Mode + 起動ロジックなら既定値の変更で済む。

### 正本 JSON の作り方・運用

- **正本 JSON の作り方はデザインソースで変わる**（取り出し方の 4 択・ルート別の手順・コミット方針は `CLAUDE.md` ステップ 6 が正。ここでは繰り返さない）。
- トークンが未定義の生の値しか無い場合、**Claude が名前を決めて勝手にトークン化しない**。§9 の診断レポートに「Variables 化されていない直値」として挙げ、どのトークンに寄せるか / どこに新設するかを操作者に決めてもらう。
- 同じ Push 先に過去の生成物がある場合は既存トークンと整合させ、無断で類似トークンを増やさない（正本 JSON 同士の diff で確認する）。
- **Style Dictionary の出力先（参照方法）はターゲットごとに決まっている**:

| ターゲット | 出力先                                                                        | 参照のしかた                                               |
| ----- | -------------------------------------------------------------------------- | ---------------------------------------------------- |
| Web   | Tailwind v4 の CSS 変数（`styles/tokens.css` の `@theme`、詳細は `web-app-styling.md` §1） | ユーティリティクラス（`bg-primary`, `text-muted`, `rounded-md`） |
| ネイティブ | 各フレームワークのテーマ定数（詳細は `native.md`）                                            | テーマ/定数参照（`theme.colors.primary` 等）                   |

- Style Dictionary の設定は **`config/sd.config.js`**（= Build Target。マルチプラットフォーム出力の分岐点。「値の差」の上書き Token はここに置く — 上の分類表参照。出力先は 1 つ＝Web から始めてよい）に置き、成果物に含めて移植先で正本 JSON から再ビルドできる状態にする。
- 命名は**意味ベース**（役割で命名し、見た目で命名しない）:
  - 色: `primary`, `surface`, `text-muted`, `border-subtle`（❌ `blue-ish`, `gray2`）
  - 余白: Tailwind 標準スケール（`--spacing` の倍数。既定では `p-1`=4px, `p-4`=16px）に乗せる。**刻みは暗記せず §9.3 で実測する**。独自の余白トークン追加は最小限
  - 角丸: `sm / md / lg`
  - タイポ: `body`, `heading`, `caption` などロール名（サイズ・ウェイト・行間のセットで扱う）
- **使う段数を絞る。** デザインソースに登録されていても、**プロジェクトのドキュメントで用途を与えていない段は使わない**（書体 66 個・角丸 11 段が登録されていても、実際に使われているのは書体 24 個・角丸 6 段ということが普通に起きる）。トークンの**出力自体は全量でよい**が、「どの段を使うか」を決めて記録する（型階層が平坦になるのを防ぐため）。
  - 逆引き表を作るときに `components.json` の `bindings` を集計すれば、**実際に使われている段が分かる**。用途を与えていない段が多い場合は、生成前に操作者へ「この段は使うのか」を確認する。

### Tailwind の予約名前空間に出さない（**出すと既定スケールが静かに壊れる**）

**照合（`--spacing` の 0.5 刻みに乗るか = §9.3）とは別の話で、こちらは「出力してよいか」の話。**
Figma のトークン名は px 値そのものになりがちなので（`Spacing/4` = 4px）、素直に変換すると次が起きる:

```css
@theme { --spacing-4: 4px; }   /* ← Tailwind 既定の p-4（16px）が 4px になる */
```

**ビルド・型検査・CI がすべて通り、画面全体の余白が静かに 1/4 になる。** 誰も気付けない種類の事故なので、出力側で防ぐ。

- **Tailwind v4 向けの出力から余白・間隔系トークンを除外し、Tailwind 標準スケールに乗せる**（`Spacing/16` → `p-4`）。
- **逆引き表には残す**（`Spacing/16` → `p-4` の形。値 → クラス名の対応は失わない）。
- **除外した旨を生成物のコメントに残す**（消えたのではなく意図的に出していないことが分かるように）。
- **雛形のガードが見るのは 7 つ**: `--spacing` / `--text` / `--radius` / `--shadow` / `--breakpoint` / `--container` / `--font`。Tailwind がこれらに意味を持つので、**既定キーと同名になる名前**（数値の段 `-4` `-16`、素の段名 `sm` `md` `lg` `2xl` `none` `full`）を出すと同じ上書きが起きる。
  - **意味ベースの名前なら衝突しない**（`--radius-card` / `--text-heading-lg` / `--spacing-gutter`）ので出してよい。
  - 衝突するトークンが必要な場合は、**上書きが意図的である旨をデザイナーと合意**してから例外にする（`web-app-styling.md` §2）。
- **`--color-*` はガードの対象外**（既定パレットは `--color-blue-500` のような 2 段の名前で、上の規則では拾えない）。**色は別の経路で担保する**: 意味ベースで命名し（§2 の命名規約）、生パレット参照は `raw-palette` 検査が拾う。
  - ただし **`raw-palette` はプロジェクトが `@theme` で再定義した色名を除外する** = **パレット名の上書きは設計上許容**（`web-app-selfcheck.md` §2）。**意図せず既定パレットと同名を出さないよう、逆引き表を作る時点で確認する。**

### 「値 → トークン名」逆引き表（コード生成の唯一の参照元）

トークンを確定したら、**コード生成に入る前に逆引き表を作ってチャットに提示する**。これが無いと、Figma から取れた生の値（`#2563EB`, `16px`）をそのままコードに書くのが最短経路になってしまう。

| Figma の値 | Figma Variable 名 | トークン名 | Web の参照 |
| --- | --- | --- | --- |
| `#2563EB` | `Color/Brand/Primary` | `color.primary` | `bg-primary` / `text-primary` |
| `#64748B` | `Color/Text/Muted` | `color.text.muted` | `text-muted` |
| `16px` | `Spacing/M` | （Tailwind 標準スケール） | `p-4` / `gap-4` |
| `8px` | `Radius/M` | `radius.md` | `rounded-md` |

- **表はデザイナーの追跡手段も兼ねる**（どの Figma 変数がどこに写ったかが分かる）。正本 JSON がその記録を保持する。
- **表に無い値はコードに書かない。** `bg-[#1a73e8]` / `w-[437px]` のような arbitrary value で埋めて済ませず、**§9 の診断レポートに回す**。
- プラグインで書き出した JSON は、① 正本 `tokens/` への取り込み（= `styles/tokens.css` の生成）と ② この逆引き表の作成の**両方**に使う。取り込んで終わりにしない。

## 3. 命名規則

- コンポーネント名は Figma のレイヤー/コンポーネント名を基に、意味のある名前へ整える（例: `Frame 12` → `PrimaryButton`）。
- 略語や連番だけの名前（`Frame`, `Group 3`）はそのまま採用しない。
- ファイル名・識別子・接頭辞は各ターゲットの規約に従う（Web の接頭辞は `config` の `componentPrefix` で任意設定: `web-app.md` §3.1）。

## 4. レイアウト

- Auto Layout の方向 → 主軸（横/縦）、間隔 → gap、パディング → padding にマッピング。
- 絶対配置は最小限に。可能な限りフローレイアウトで表現する。
- サイズは固定値を避け、内容に応じて伸縮する指定を優先（min/max を活用）。

## 5. テキスト

- テキストはベタ書きせず、可能なら props / 変数として外出しできる形にする（再利用コンポーネントの場合）。
- 多言語の可能性がある文言は、ハードコードである旨をコメントか報告で明示する。

## 6. アセット（画像・アイコン）

- アイコンは可能な限りベクター（SVG 等）で取得し、作業ツリーの `assets/` に保存。
- 画像は適切な解像度で書き出し、参照パスを相対で記述。
- 装飾目的の画像には空の代替テキスト、意味のある画像には適切な代替テキストを付ける。

## 7. アクセシビリティ

- 見出し階層、ボタン/リンクの区別、フォーム要素のラベル付けを守る。
- 色のコントラストが不足していそうな箇所は、**生成前に §9 の診断で挙げる**（勝手に色を変えて解決しない）。
- インタラクティブ要素にはフォーカス可能・操作可能なマークアップ/実装を用いる。

## 8. 未対応・要確認の扱い

- 自動変換が難しい箇所（複雑なインタラクション、アニメーション、条件表示など）は
**勝手に作り込まず**、TODO コメントを残しつつ報告する。
- **デザインソース側の設定不足・誤りも「勝手に対応しない」対象**。§9 の診断レポートで操作者に返す。

## 9. 変換前診断（3 カテゴリ。**すべて毎回通す**）

デザインソースの設定が不足・誤っていることは日常的にある。**推測で補完すると、間違いがコードに焼き込まれたまま誰も気付けなくなる**。
そこで**コード生成に入る前に**「何が問題になるか」と「どう直すか」を洗い出し、操作者に返して判断させる。Claude が決めない。

**実施タイミング・提示のしかた・A/B/C の分岐は `CLAUDE.md` ステップ 7 が正。** このファイルは**何を検出し、何を書くか**を定める。

> **自作プラグインの出力に「レイアウトの事実」と自己検証が含まれている場合、①② の大半は目視ではなく機械的に判定できる。**
> 例: `figma-plugin-airis.md` の `components.json.layout` + `validation`（該当する `tokens.customPluginSpec` が設定されているときは、そのルールの診断節を先に読む）。

**検出は 3 カテゴリ。①だけ見て終わるのが診断漏れの典型なので、②③ を必ず通す**:

| | カテゴリ | 何を見るか | 検査に必要な前提 |
| --- | --- | --- | --- |
| **①** | デザインソースの不備 | 設定されているべきものが設定されていない | なし（ターゲット非依存） |
| **②** | 設計の抜け | **描かれていない**もの（状態・エッジケース・レスポンシブ） | なし |
| **③** | アーキテクチャ非適合 | 描かれているが**採用スタックで表現できない** | **ターゲット・ルール・トークンの確定**（`CLAUDE.md` ステップ 3〜6） |

**書き方の原則（全カテゴリ共通）**:

- 各項目は「**どこが**・**何が問題か**・**どう直すか**」の 3 点を必ず埋める。「トークン化されていません」だけでは操作者が行動できない。
- **数値のズレには寄せ先の候補を必ず添える**（例: `padding 13px → p-3(12px) か p-3.5(14px)`）。候補は §9.3 のスクリプトの出力をそのまま使う。候補なしで「スケールに乗りません」だけ言わない。
- **該当ゼロのカテゴリは 1 行**（「①: 問題なし」）。該当しない項目を並べて長くしない。

### 9.1 ① デザインソースの不備

| 検出するもの | 提示する内容 |
| --- | --- |
| **Variables 化されていない直値** | どのレイヤーのどのプロパティか / どの Variable を作って割り当てるか（既存トークンで代替できるならその名前も） |
| **逆引き表に無い値**（§2） | 値と使用箇所 / 既存トークンに寄せるか、新トークンを `core` / `product/<名前>/mode/default` のどちらに足すか |
| **Auto Layout でない絶対配置** | 該当フレーム / Auto Layout の方向・gap・padding をどう設定するか |
| **連番・無名レイヤー**（`Frame 12`, `Group 3`） | 対象の一覧 / 役割が分かる名前の付け方 |
| **部品名・プロパティ名の規約違反**（下記のとおり**機械検査する**） | 現在名 → 規則を満たす候補（満たせない場合は理由）/ 真偽値プロパティの `is` / `has` 打ち分け |
| **意味ベースでない Variable 名**（`blue2`, `gray-light`） | 現在名 → 推奨名（`color.primary`, `color.border.subtle` 等。§2 の命名規約） |
| **コンポーネント化されていない繰り返し要素** | 該当箇所 / Component にすべき単位 |
| **アイコンがベクターで取り出せない** | 該当アイコン / Figma 側で必要な対応（アウトライン化・Export 設定） |
| **自動変換できない挙動**（複雑なインタラクション・アニメーション・条件表示） | 何が読み取れなかったか / 実装側に何を伝える必要があるか |

#### 命名は目視で確認しない（**機械検査する**）

部品が増えると目視では必ず見落とす。`components.json` があるなら機械で判定できる:

```bash
node scripts/lint-naming.mjs                     # 既定 tokens/.meta/components.json
node scripts/lint-naming.mjs <components.json のパス>
```

- 検査するのは **部品名**（PascalCase・`/` で 2 階層まで）/ **バリアント軸名**（1 語。CVA の variant キーになる）/ **プロパティ名**（camelCase）/ **真偽値プロパティの接頭辞**（`is` / `has`。`can` / `should` も許容。`web-app.md` §3.2）。
- **`#id` サフィックスは判定前に剥がす**（`Button #152:110` → `Button`）。これはプラグインが付ける同名退避の印であり命名の問題ではない（同名自体は `pathConflicts` が報告する）。表記ゆれ（`Dot-indicator`）はそのまま検出される。
- **ブランドロゴは部品ごと検査対象外**（`logos/` / `logo/` / `brand` で始まる名前。**プロパティも含めて丸ごとスキップする**）。表記はブランド側の資産なので直させない。ロゴ部品のプロパティ名を検査したいときは名前を変えるしかない。
- **機械変換した候補が規則を満たすときだけ提案する。** 満たせないときは置換案ではなく理由を出す（「英語名を付けてください」等）。
- **綴り間違いは機械判定できない**（軸名の `Siza`、値の `Learge` 等。1 語・camelCase の規則は満たしてしまう）。**ここだけ目視で確認する**。
- **終了コードは「違反がある」と「検査できていない」を区別する**: `0` = 検査できた（違反があっても既定では落とさない）/ `1` = `--strict` 指定時に違反あり / **`2` = 読み込めなかった**（ファイルが無い・JSON が壊れている）。
  - **CI では違反で落とさない**（デザイン起因なので Figma を直すまで無関係な PR まで止まる）。ただし **`2` は落とす** — 「検査できていない」のに緑になるのを防ぐ。届け方は `web-app-testing.md` §6。
  - `GITHUB_ACTIONS=true` のときは PR の注釈とジョブのサマリを自分で出す（スクリプト側に実装済み）。
- **これも CSS/JSON の読み取りだけ**なので `CLAUDE.md` 原則 2 の対象外。

### 9.2 ② 設計の抜け（Figma に「描かれていない」もの）

**ここが最も見落とされやすい。** 描かれていないものは、指摘しなければ**実装時に Claude が発明する**ことになる。
「デザインに無いから作らない」のではなく、**「無いので決めてください」と返す**のが正しい。

| 検出するもの | 提示する内容 |
| --- | --- |
| **インタラクション状態の欠落** | どの部品に何が未定義か（`hover` / `focus-visible` / `active` / `disabled` / `loading` / `read-only`）。**ストーリーとして列挙する対象**なので、無いと Storybook のカバレッジが穴になる |
| **フィードバック状態の欠落** | `error`（文言と位置）/ `success` / 送信中 / 送信後 |
| **データのエッジケース** | 空（0 件）/ 1 件 / 大量 / 長文でのはみ出し（折り返す？ 省略記号？）/ 画像なし / 数値の桁溢れ |
| **レスポンシブの欠落** | 設計済みのフレーム幅は何か / 他の幅ではどう振る舞うか（要素の並び替え・非表示・折り返し） |
| **フォームの仕様欠落** | 必須マーク / バリデーションのタイミングと文言 / 初期値 / 入力補助（`autocomplete`） |
| **キーボード操作・フォーカス順序** | Tab 順 / `Esc` で閉じるか / 開いた直後のフォーカス位置（ダイアログ・メニュー） |
| **コントラスト不足**（下記のとおり**実測する**） | 前景色 / 背景色 / **実測したコントラスト比** / 満たすべき基準（WCAG AA = 4.5:1、大きい文字 3:1）/ **寄せ先候補**（基準を満たす既存トークン、または明度だけ変えた提案値） |
| **文言の可変長・多言語** | 伸びたときの想定 / 翻訳予定があるか |

#### コントラストは目視で判断しない（**実測する**）

**「薄そう」で挙げても「大丈夫そう」で見逃す。** トークンの値は分かっているので、**比は計算できる**:

```bash
# 前景:背景 の組み合わせを渡す（クラス名 / トークン名 / 生の色のどれでもよい）
node scripts/contrast.mjs <作業ツリー> text-content-muted:bg-surface text-primary:bg-surface

# 大きい文字（24px 以上 / 18.66px 以上の太字）だけを見るときは基準を 3:1 に切り替える
node scripts/contrast.mjs <作業ツリー> text-content-muted:bg-surface --large
```

- **渡すのは「デザインで実際に重なっている組み合わせ」**（テキストと下地、プレースホルダと入力欄、リンクと背景など）。総当たりはしない。
- **地（背景）の指定が無い部品も必ず 1 組は測る。** `bindings` に `fills` が無い部品は、**置かれる面を仮定して測る**（既定は白 = `surface` / 画面背景トークン）。**背景が親から継承されている組み合わせは Figma のデータから読み取れない**ため、「抽出できたものだけ測る」と**確実に取り逃す**。
  - 特に見落としやすいもの: **表の見出し / 補足説明 / キャプション / プレースホルダ / 非活性でない薄い文字**。
- **Disabled 状態は比の対象外**（WCAG 1.4.3 の例外: 無効な UI 部品の文字にはコントラスト要件が無い）。測ってもよいが、**未達として報告しない** — 直す必要のない宿題をデザイナーに渡すことになる。
  - 一方で**プレースホルダは対象内**。薄すぎるものは報告する。
- **出力の「寄せ先候補」をそのまま採用しない。** 基準を満たす既存トークンと、明度だけ変えた提案値が出るので、**どれにするかはデザイナーが決める**（`CLAUDE.md` ステップ 7 の A/B/C）。
- **これは a11y の CI（`web-app-testing.md` §2）より前に置く層**。CI でも同じ違反は落ちるが、そこまで行くと「Figma を直す → 再エクスポート → 再生成 → 再 Push」の往復が 1 周増える。
- **`@theme` が読めない**（`npm ci` 前・`tokens.css` 未生成）ときは判定できない。**その場合は「未実施」と報告する**（目視の推測で埋めない）。

### 9.3 ③ アーキテクチャ非適合（ターゲット確定後にのみ検査可能）

**採用スタックの語彙・スケールに乗るかを機械的に照合する。** 乗らない値を放置すると、実装時に `p-[13px]` のような
arbitrary value や独自実装として静かに埋められ、以後トークンの外に出てしまう。

#### Web 共通 — 数値スケールの照合（**実測する。数値を暗記・ハードコードしない**）

Tailwind のスケールは**バージョンとプロジェクトの `@theme` で変わる**。このリポジトリに数値表を持つと必ず腐るので、
**毎回、対象リポジトリの実効スケールを読み取って照合する**。

```bash
# 実効スケールの一覧
node scripts/effective-scale.mjs <対象リポジトリのパス>

# Figma から拾った値をまとめて判定（寄せ先候補まで出る）
node scripts/effective-scale.mjs <対象リポジトリのパス> spacing:13px radius:20px text:15px weight:620 bp:1200px
```

- スクリプトは **① `node_modules/tailwindcss` 内の `@theme`（= 使っている版の既定テーマ）→ ② プロジェクトの `@theme`（`styles/tokens.css` 等）** の順に読み、後勝ちで実効スケールを組む。ファイル名は決め打ちせず `@theme` を含む CSS を探すので、**Tailwind の版が上がっても追従不要**。
- **これはビルドでもテストでもなく CSS の読み取り**なので、`CLAUDE.md` 原則 2（Push 前にローカルで実行しない）の対象外。診断のために実行してよい。
- 判定の種類:

  | 判定 | 意味 | 診断での扱い |
  | --- | --- | --- |
  | `OK` | スケールに乗る | 報告不要 |
  | `OFF-SCALE` | 乗らない | **寄せ先候補を添えて報告**し、どちらに寄せるか操作者に決めさせる |
  | `MANUAL` / `ERROR` | 数値比較できない（色・影・解釈不能） | 目視で照合し、判断がつかなければそのまま報告する |
  | `UNKNOWN` | 基準となる `--spacing` 自体が読めない（`calc()` 等） | **「適合」と断定しない。** 判定が劣化している合図なので「未実施」として報告する |

- **スケールの性質はプロパティで違う**（スクリプトが出力で明示する）:
  - **倍数ルール**: 余白・間隔・サイズ（`--spacing` の **0.5 刻み**の倍数。`p` `m` `gap` `w` `h`）
  - **離散スケール**: 角丸・文字サイズ・フォントウェイト・行間・字送り・ブレークポイント・最大幅・ブラー
  - **数値比較不可**: 色・影（多重シャドウ・spread は 1 クラスに乗らない。グラデーション・ブレンドモード・背景ブラーも同様）
  - ⚠️ **この 2 種を混同しない。** 角丸 `20px` は「4 の倍数だから OK」ではない（離散スケールに 20 が無ければ非適合）。判定はスクリプトに任せる。
- **色は「プロジェクト定義のトークンだけ」を使う。** スクリプトは Tailwind 既定パレット（`blue-500` 等）を「生成コードでは使わない」と明示して件数だけ出す。パレット直参照は非適合として報告する。
- **スケールを取得できなかった場合**（対象リポジトリで `npm ci` 前など。スクリプトは終了コード 1 と警告を返す）:
  - **「適合している」と断定しない。** 「Tailwind のスケールを取得できなかったので数値の照合は未実施」と正直に報告し、拾った値の一覧だけを提示して操作者に判断を仰ぐ。
  - 対象リポジトリで `npm ci` を実行してから再試行するのが本筋（実行してよいか確認する）。
- **判定の入力は 2 つある。片方だけでは足りない**:
  1. 逆引き表（§2）で拾いきれなかった**トークンの値**
  2. `components.json` の `layout` に入っている**実数値** — `gap` / `pad` / `r` / `sw`、および `wSize` / `hSize` が `FIXED` のときの `w` / `h`
  - **2 を忘れると「トークンには無いが実装される数値」が丸ごと抜ける**（51×31 のスイッチ、9px の余白、61px の高さ、1.5px の枠線、14px の角丸など）。逆引き表 → スクリプト → どちらにも乗らなければ非適合として報告、という順に通す。
  - ただし `layout.children[]` の `w` / `h` のうち **`HUG` のものは測定結果**なので照合対象から外す（含めると「テキストの実測幅 7px」のようなノイズが大量に出る）。
- **余白の刻みは `--spacing` の 0.5 倍まで**（`p-0.5` = 2px / `p-1.5` = 6px / `h-13.5` = 54px）。Tailwind は `calc(var(--spacing) * <数値>)` を作るのでここまでは有効な値であり、**`OFF-SCALE` にしてはいけない**。
  - **`effective-scale.mjs`（診断）と `class-exists`（生成後の検査）は同じ規則で判定する。** 片方だけ整数倍にすると、**診断が「直せ」と言い検査が「OK」と言う**状態になり、どちらを信じるか決められない。**片方だけ直さない。**
  - これを守らないと、**Figma の正しい値を「スケールに乗らないので直してください」とデザイナーに突き返す**ことになる。原則 3 を守るための道具が、存在しない不備を報告して誤った修正を要求する状態になるので、`class-exists` の誤検知（単なるノイズ）より有害。
- **`MANUAL` / `ERROR` / `UNKNOWN` は「適合」ではない。** スクリプトの末尾は非適合件数と**判定していない件数を別に出す**。「全件適合」と読み替えて報告しない。
