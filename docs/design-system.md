# デザインシステムの考え方

Spotify Encore を参考にした層構造になっています（**詳細な設計根拠は [`rules/common.md`](../rules/common.md) §2**）。

```
【トークンの構造】        Core（最小限） + product/<名前>/mode/（default + 必要なモード）
【ビルドターゲット】      Style Dictionary の出力先
【共有インターフェース】  Storybook（デザイン意図と実装の答え合わせの場）
【実装の土台】            Component 実装（shadcn/ui + Tailwind）/ Behavior（Radix = 選定済み依存・デザイン意思決定の外）
```

```
tokens/
├── core/                     # ブランドの根源（最低限: ロゴ・スペーシング・表現原則）
└── product/<プロダクト名>/mode/
    ├── default/              # 必須。プロダクトの作り込みはここが主戦場
    ├── README.md             # モードと利用シーンの対応マッピング
    └── dark/ など            # 必要になったら追加する差分（先回りで作らない）
```

- **Core は最低限**。上から決めるのはブランドの根源だけで、**プロダクトの個性は `product/` 側で作り込みます**（UI の全体感まで画一化すると「どの画面も似たり寄ったりで飽きる」ため。目指すのは統一ではなく調和）
- 適用順は `core` → `mode/default` → `mode/<モード>`（有効時のみ）。**差分が無ければ Core がそのまま流れるのが正常形**です
- **共通化は「下から昇格」**: トークンもコンポーネントも、**2 プロダクト以上で同一用途が発生してから**共通層へ上げます（1 プロダクトでの汎用化予測は禁止）。昇格前はプロダクトローカルに置いて OK
- **Storybook が、デザインの意図と実装が答え合わせをする唯一の接面**（公式カタログ）。見た目の合否判定は、stories の実装とは切り離して行います
- **VRT（見た目の回帰テスト）は昇格済みコンポーネントのみ対象**（差分ノイズ対策）。差分の合否判定は機械ではなく人が行います

**Airis が「勝手にやらない」こと** — トークンの値を増やす／共通層に置く／VRT 対象に加える／**Figma 側の設定不足を補完する**。いずれも候補を報告するだけで、判断はあなたがします。
